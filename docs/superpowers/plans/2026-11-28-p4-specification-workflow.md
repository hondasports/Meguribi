# P4 Specification and Workflow Implementation Plan

**Spec:** `docs/superpowers/specs/2026-11-27-multi-agent-orchestration-design.md`（§6.4、§6.5）

## Scope of this owner

This plan covers the P4 specification foundation owned in this worktree assignment:

- `packages/core/src/specify/*`: specification types, approved-conclusion validation, seed trace validation, artifact construction, RunStore persistence helpers.
- `packages/schemas/src/specification.ts`: Valibot schemas for specification content and persisted specification artifacts.
- `packages/adapters/src/specify/*`: read-only `specifier` RoleAgent invocation, JSON extraction, schema validation, repair retry, cancellation propagation.
- exports required by the follow-up workflow implementation.

Out of scope for this owner: workflow step registration, CLI wiring, PR body rendering, and end-to-end `discuss-to-pr` orchestration.

## Design decisions

1. Reuse the existing `RequirementArtifact` shape and `RequirementArtifactSchema`; do not create a parallel requirement model.
2. Persist exactly two RunStore artifacts for the specify step: `requirement.json` and `specification.json`.
3. `Specification.acceptanceCriteria[]` traces every criterion to exactly one `DiscussionConclusion.acceptanceCriteriaSeeds[]` item through `seed`.
4. Seeds without a corresponding criterion are not silently dropped. They are copied into `Specification.openQuestions` with an explicit prefix. Criteria that cannot be mapped one-to-one (unknown seed, duplicate criterion for one seed, or duplicated seed in the conclusion) are excluded from machine-readable acceptance criteria and preserved as explicit `openQuestions` instead of being guessed or arbitrarily selected.
5. Before artifact construction, call `assertApprovedConclusion` with the persisted approval and current conclusion hash. Hash mismatch stops specification generation.
6. `requirementIds` that do not reference a requirement emitted by the specifier are removed from machine-readable `mapsTo` / `requirementIds` and recorded as `openQuestions`; Meguribi does not guess the intended requirement.
7. The `specifier` session is read-only. External issue/discussion content is represented as untrusted material in the prompt, delimiter-like tags are escaped, and token/URL/email-like diagnostic strings are redacted before sending.
8. Aborting during a specifier send propagates `code: "cancelled"` and closes the session; no artifacts are saved by the caller in that case.

# P4 discuss-to-pr workflow / CLI production wiring plan（orchestration owner）

**Owner scope:** `discuss-to-pr` 組み込みワークフロー定義、本番ユースケース（orchestration）、CLI 配線（`workflow run`・approve 継続）、implementer ≠ reviewer ポリシー、PR 本文への仕様反映、fixture 通し試験、P4 日英ドキュメント。D の specify API（`buildSpecificationArtifacts` / `saveSpecificationArtifacts` / adapters specifier）に接続し、specify 内部には踏み込まない。

## Design decisions

1. `discuss-to-pr` は §6.5 の YAML どおりの組み込み定義とし、`validateWorkflowDefinition` を通す。`discuss` → `approve(of: discuss)` → `specify` → `plan` → `implement` → `verify` → `review(onChangesRequired: goto fix, max 3)` → `fix(then: verify)` → `publish`。
2. 無人自動承認は禁止（§6.3 A1）: `approve` 工程は承認記録がなければ `awaiting_human` で停止してプロセスを終了する。`--non-interactive` でも自動承認オプションは設けない。
3. 承認後の継続: `meguribi approve <runId>` は承認記録（承認者・日時・conclusion ハッシュ）を保存したうえで、**同一プロセスで** `specify` 以降を実行する。`startAt` による engine 再開ではなく、orchestration が approve 後の工程列を直接駆動する（delivery 既存の `createDeliveryStepHandlers` を再利用）。
4. ハッシュ照合（§6.3/§6.4）: specify 開始時に `approval.json` の結論ハッシュと現在の `conclusion.json` を照合し、不一致なら停止。D の `assertApprovedConclusion` に委譲する。
5. `plan` には仕様の受け入れ条件を `completionCriteria` として渡す（A3 対策）。`review` は既存の `ReviewRequirementCoverage` による判定を再利用する。
6. implementer ≠ reviewer: wiring 時に `roles.implementer` と `roles.reviewer` のプロファイルが同一なら `RoleAssignmentError` で起動前に停止する。
7. 仕様の保存: `specification.json` / `requirement.json` は RunStore に保存（D の helper）。PR 本文には受け入れ条件を含めて render する。対象リポジトリには commit しない。
8. 通常の delivery を保護: 既存 `run` / `resume` / delivery fixture テストは無変更で通す。discuss-to-pr は独立した定義・ユースケースとして追加し、delivery 本体は触らない。
