# プロダクト構想と成長ループ

## 1. 目的

Meguribi の目的は、AI にコードを書かせること自体ではありません。

次の流れを、既存 GitHub リポジトリ上で途切れさせずに回すことです。

```text
観測
  -> 課題候補
  -> 原因仮説・解決仮説
  -> 検証
  -> 課題の確定
  -> 要件化
  -> 実装
  -> Pull Request
  -> リリース
  -> 効果測定
  -> 次の仮説
```

Meguribi はこの流れに必要な情報を整理し、Codex と Devin に適切な役割を割り当て、GitHub 上に判断の履歴を残します。

## 2. 想定利用者

- 複数の既存リポジトリを個人で開発・保守している開発者
- GitHub Issue と Pull Request を中心に運用している人
- BIZ / Product の壁打ちと実装を AI で補助したい人
- AI に完全自動運転させるのではなく、重要な判断は自分で行いたい人

## 3. 解決する問題

コーディングエージェント単体では、次の問題が残ります。

- 実装しやすい要求だけが優先される。
- Issue の背景や仮説が PR まで引き継がれない。
- AI が課題を事実として断定する。
- 実装完了がプロダクト上の成功として扱われる。
- Codex と Devin の責務が混ざる。
- テスト成功が AI の自己申告に依存する。
- 普段の作業ディレクトリと AI の変更が混ざる。

Meguribi は、GitHub と構造化成果物を境界にしてこれらを抑制します。

## 4. 基本概念

### 4.1 観測

確認済みの事実です。

例:

- 入力画面を開いた利用者の 25% が登録を完了していない。
- 同じ操作に関する問い合わせが 3 件ある。
- 特定のテストが頻繁に不安定になる。

AI が推測した内容を観測として扱ってはいけません。

### 4.2 課題候補

観測から推定される、ユーザーまたはプロダクト上の困りごとです。

例:

- 一部の利用者が支出登録を完了できていない。

この段階では原因や解決策を断定しません。

### 4.3 原因仮説

課題が起きる理由の仮説です。

例:

- カテゴリ選択が負担になり、登録途中で離脱しているのではないか。

### 4.4 解決仮説

課題を改善する方法の仮説です。

例:

- 金額だけで仮登録できれば、登録完了率が改善するのではないか。

### 4.5 反対仮説

有力な仮説が誤っている可能性を表します。

例:

- 入力項目ではなく、アプリを開く習慣がないことが主因ではないか。
- 入力項目を減らすと記録価値が下がり、継続率が悪化するのではないか。

Meguribi は、原因仮説・解決仮説と同時に反対仮説を生成します。

### 4.6 要件

検証済みの課題と採用した解決方針から、実装可能な振る舞いへ落としたものです。

要件には最低限、次を含めます。

- 解決する課題
- 対象ユーザー
- 必須の振る舞い
- 完了条件
- 対象外
- 成功指標
- ガードレール指標
- 関連する Hypothesis / Problem Issue

## 5. Issue の流れ

```text
Hypothesis Issue
  -> Problem Issue
  -> Requirement / Feature Issue
  -> Pull Request
  -> Measurement Issue
  -> Next Hypothesis Issue
```

### 5.1 Hypothesis Issue

目的:

- 観測を整理する。
- 課題候補を明示する。
- 原因仮説、解決仮説、反対仮説を作る。
- 検証方法と判定条件を定義する。

AI は Issue 草案を作れますが、仮説の採用は人間が判断します。

### 5.2 Problem Issue

目的:

- 検証結果から、解く価値がある課題を確定する。
- 誰が、どの状況で、何に困っているかを記録する。
- 解決策をまだ固定しない。

### 5.3 Requirement / Feature Issue

目的:

- 選んだ解決方針を実装可能な要件へ変換する。
- 完了条件と対象外を確定する。
- 実装開始を承認する。

### 5.4 Measurement Issue

目的:

- 元の仮説と成功条件を引き継ぐ。
- リリース後のデータと定性的反応を記録する。
- 継続、改善、拡大、撤回、保留を判断する。

## 6. AI の役割

### Codex

- 既存 Issue や資料から課題候補を抽出する。
- 仮説・反対仮説・検証方法を提案する。
- 課題を要件へ構造化する。
- 対象リポジトリを調査し、技術計画を作る。
- 実装差分とテスト結果をレビューする。

### Devin

- 承認済みの要件と Codex の技術計画に基づいて実装する。
- 必要なテストを追加する。
- 指定された worktree 内だけを変更する。
- 未解決事項を成果物に記録する。

### Meguribi

- Issue とリポジトリの文脈を取得する。
- Codex と Devin へ渡す入力を構築する。
- 両者の成果物を保存し、直接会話させない。
- worktree、ブランチ、検証、PR を管理する。
- 人間承認が必要な箇所で停止する。

## 7. 人間が介入するタイミング

### 必須

1. 仮説を課題として採用するとき。
2. 解決方針と MVP スコープを選ぶとき。
3. 高リスクな実装を開始するとき。
4. Pull Request をマージするとき。
5. リリース結果を成功・失敗として評価するとき。

### 条件付きで省略可能

低リスクなバグ修正、文言修正、テスト追加、ドキュメント変更では、技術計画後の実装開始承認を省略できます。

### 常に人間判断に残すもの

- 誰の課題を優先するか
- 課金、契約、個人情報、認証・認可の方針
- データ削除
- 大きなアーキテクチャ変更
- 本番リリース
- 自動マージ

## 8. 標準フロー

### 新機能

```text
meguribi discover
  -> 人間が候補を選択
meguribi hypothesis
  -> 人間が検証方針を承認
meguribi promote
  -> 人間が課題として採用
meguribi require
  -> 人間が要件・対象外・成功条件を承認
meguribi run
  -> Codex 計画 -> Devin 実装 -> 検証 -> Codex レビュー -> Draft PR
人間が PR をマージ
meguribi measure
  -> 人間が結果を評価
```

### バグ修正

```text
Bug Issue
  -> meguribi plan
  -> meguribi run
  -> Draft PR
  -> 人間がマージ
```

バグ修正では、原則として仮説・課題への昇格フローを省略します。

## 9. 成功条件

Meguribi 自体の成功は、生成コード量ではなく次で判断します。

- Issue の背景と PR の差分が追跡できる。
- 要件外変更が減る。
- AI の出力を人間が短時間で判断できる。
- 実装後に元の仮説へ戻って評価できる。
- AI の失敗時に、安全に停止・再実行・破棄できる。
- 個人がコードを読み、仕組みを修正できる小ささを保てる。

## 10. 非目標

MVP では次を扱いません。

- 複数ユーザー・複数組織向け SaaS
- 常駐 Web サーバー
- Web ダッシュボード
- 自動ロードマップ決定
- AI による自動マージ
- 多数のエージェントによる自由討論
- 複数 Issue の大規模並列実行
- 独自の Issue トラッカーやコードホスティング
