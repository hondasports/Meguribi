# Meguribi 共通実装スキル

## 使うタイミング

Meguribi のコード、設定、スキーマ、テスト、ドキュメントを変更するすべての作業で使用します。

## 先に読む

- `AGENTS.md`
- `docs/ja/product-and-workflow.md`
- `docs/ja/architecture.md`
- `docs/ja/implementation-roadmap.md`
- 対象 Issue と関連コメント

## 目的

Issue の範囲を守りながら、小さく、安全で、追跡可能な変更を作ります。

## 基本判断

1. 要求を「必須」「対象外」「未確定」に分ける。
2. 現在の Phase と Issue の位置付けを確認する。
3. 既存アーキテクチャで解けるか確認する。
4. 変更するアダプター・ユースケース・スキーマを特定する。
5. 失敗時の停止点と復旧手順を先に決める。
6. 必要なテストを実装前に列挙する。

## 実装原則

- CLI、ユースケース、アダプター、ドメイン型を分離する。
- 外部ツール固有の JSON や stdout をコアへ漏らさない。
- 入力は境界で Valibot 等により検証する。
- 状態遷移は明示的な型と関数で表す。
- side effect はアダプターへ閉じ込める。
- 同じ入力で再実行しても、コメントや PR を無制限に重複させない。
- 自動化より停止可能性、観測可能性、再現性を優先する。

## Issue 駆動の作業手順

1. Issue の完了条件を箇条書きへ正規化する。
2. 関連ドキュメントと現在の実装を確認する。
3. Issue 専用ブランチと worktree を用意し、作業ルートをその worktree へ切り替える（`AGENTS.md` §9）。
4. スコープ外の提案は実装せず、PR の補足へ分離する。
5. 最小の変更単位を実装する。
6. 対応するテストを追加する。
7. 検証コマンドを実行する。
8. 変更ファイル、判断、未解決事項を要約する。

## 禁止事項

- Issue にない DB、Web UI、daemon、queue、cloud service の追加
- Codex と Devin の直接的な再帰呼び出し
- default branch への直接変更
- 自動マージ
- agent の自然言語による自己検証を成功根拠にすること
- secret のログ・fixture・コードへの保存
- 理由のない共通化や汎用フレームワーク化

## 完了条件

- Issue の完了条件との対応が説明できる。
- アーキテクチャ境界を破っていない。
- エラーと停止条件が明示されている。
- 必要なテストが追加されている。
- ドキュメントとスキルの更新要否を確認した。
